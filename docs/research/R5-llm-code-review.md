## Findings

### Q1 — How commercial review agents structure their review (prompt design, per-file vs. whole-diff, linter grounding, multi-pass)

**No vendor runs a single "review this diff" prompt. The verified production shape is a pipeline: deterministic/static-analysis grounding → repo-context gathering → one or more LLM review passes with a fixed output contract → structured routing of findings.**

- **CodeRabbit — orchestrated system, tools as hints.** "CodeRabbit orchestrates an entire system for every single review. This isn't a simple 'review this changeset' prompt to an LLM. It's a production-grade AI infrastructure" [verified: fetched, S2]. Behind each comment: "Sandboxed cloud execution with your full repository cloned", "Multi-dimensional code analysis combining 50+ static analyzers, linters and SAST tools", "Agentic exploration that autonomously investigates your codebase for context", "Specialized AI agents working in parallel: Review, Verification, Chat, Pre-Merge Checks, and Finishing Touches", and "Living memory that learns from your feedback, PRs, issues, and coding guidelines" [verified: fetched, S2]. The LLM/static-analysis boundary is explicit: "CodeRabbit runs third-party linters and security scanners during the review and passes their findings to the review model as hints. When an inline review comment covers lines that have tool findings, the comment ends with a collapsed 🧰 Tools section that lists those findings with each tool's own severity and rule ID" — i.e., deterministic findings are attributed to the tool, not re-derived by the model [verified: fetched, S1]. Review cadence is two-tier: "Full comprehensive review when a new pull request is created" and "Incremental review when existing pull requests receive new commits — Focus on newly added changes… Maintains conversation context" [verified: fetched, S1].
- **Qodo — multi-agent, architect-framed.** "Qodo combines multi-agent review, deep repository context, and continuous learning" [verified: fetched, S14]. Specialized agents evaluate "from multiple perspectives" (bugs, rule violations, requirement gaps, UX deviations, cross-repo conflicts, skill-related findings) and "draw on four sources of context: your full codebase and its architecture, your pull request history, linked tickets and requirements, and your organization's standards and policies. They assess changes as a principal software architect would, not as isolated diffs" [verified: fetched, S14]. Multi-pass rationale: "Combining multiple review agents with shared context lets Qodo catch what a single-pass review misses, while filtering out low-impact or irrelevant comments before they reach the pull request" [verified: fetched, S14].
- **Greptile — graph context + tiered effort + a published build blueprint.** Greptile indexes a "complete graph of your codebase" (files/functions/classes/variables, calls, imports, dependencies) and, per changed function, queries dependencies, usage sites (impact analysis), and pattern consistency ("Suggests: 'Use parameterized queries like other DB functions'") [verified: fetched, S11]. Review depth is tiered (Base/Plus/Apex; "Higher tiers take longer, catch more, and cost more credits"; per-org default with per-repo/directory overrides or per-PR auto) [verified: fetched, S9, S13]. Greptile's 2026 "How to build a code review agent" post is the most explicit vendor description of prompt/pipeline design: a naive sandbox+LLM agent "You can probably build this in a day" but fails (misses bugs, no codebase understanding, $3–20 per run × 2–3 runs per PR, nitpicks, "keeps finding new bugs every time you run it instead of reporting everything at once") [verified: fetched, S7]. Their five improvements: (1) prompt — "instruct it to look for specific types of bugs, and also specifically tell it not to make nitpicky comments"; (2) model inversion — reviewer from a different model family than the author ("the author and reviewer will have similar blind spots"; catch rates "+~10%"); (3) context — "build an MCP gateway to give it access to your docs and your Jira, Linear, docs etc." + a codebase indexer/wiki that also "track[s] reverts and incidents"; (4) autonomous testing (dev server + computer use over "a mapping of codebase sections to testable user flows"); (5) cost — cheap models for file triage, "a narrower, higher signal set of files can then be passed into the frontier model" [verified: fetched, S7].
- **GitHub Copilot — effort-scaled agentic review.** Effort levels Lite/Balanced/Max with "Adaptive to let Copilot choose Lite, Balanced, or Max based on the complexity and risk of your pull request" (capped by org maximum); agentic capabilities including "full project context gathering" run on GitHub Actions [verified: fetched, S18].
- **Sourcery — fixed output anatomy.** Summary in the PR description ("what the change does and where the risk is"), a Reviewer's guide ("a table of what changed in each file and why"), labeled per-line inline comments (`issue (bug_risk):`, `nitpick (performance):`, security 🚨; rule violations "quotes the rule it breaks and links to it"), suggestion blocks, and a single status check (Success = "no blocking issues", Failure = "blocking security findings require changes") [verified: fetched, S19].
- **Graphite — rules with metrics.** Custom prompts ("Each rule addresses one specific concern") or file-based rules referencing repo docs, plus comment exclusions, all shown "with their metrics" in the dashboard [verified: fetched, S30].

**Per-file vs. whole-diff.** [inferred, from the verified pieces above] Every vendor splits the review into (a) a PR-level pass (summary/walkthrough/risk) and (b) per-file/per-line inline findings, with repo context attached to (b). The unit of LLM analysis is a file/hunk plus retrieved surrounding context (Greptile's graph queries around the changed function [S11]; Qodo's "not as isolated diffs" [S14]; CodeRabbit's agentic exploration over a full clone [S2]) — not the raw whole diff in one prompt. The whole-diff view is reserved for the cheap summary pass and for scoping decisions (size, risk, effort level) [S1][S18][S19].

**Linter/static-analysis grounding.** Verified pattern: run deterministic tools first, pass their findings to the LLM as hints or attribution, and explicitly defer style to linters — "Linters and formatting tools should own style" [S3]; "Turn off a tool that duplicates a linter you already run, or point it at your own configuration file" [S3]; tool findings keep "each tool's own severity and rule ID" [S1]; Greptile can drop the whole `style` comment type [S8]. [inferred] The LLM's job is therefore correctness/security/logic that linters cannot see, not re-emitting linter output.

**Multi-pass designs.** Verified instances: CodeRabbit's parallel specialized agents (Review, Verification, Pre-Merge Checks, Finishing Touches) [S2]; Qodo's multiple review agents with shared context [S14]; Copilot's Max = "multiple high-reasoning models" [S18]; Greptile's tiered depth [S9]; and the academic mirror — ICML 2025's "multi-role LLM framework" for key-bug inclusion plus a separate "filtering mechanism for FAR reduction" [verified: fetched, S24]. [inferred] The common decomposition is: generate findings (per file/hunk, possibly multiple roles/perspectives) → filter/route (severity, relevance, learned suppressions) → summarize (PR-level).

### Q2 — Severity calibration: actionable vs. noise, taxonomies in practice, avoiding nitpick flooding

**Taxonomies in practice (all fetched):**
- CodeRabbit: five levels with behavioral definitions — "🔴 Critical — Severe issues that could cause system failures, security breaches, or data loss; 🟠 Major — Significant problems that impact functionality or performance; 🟡 Minor — Issues that should be addressed but don't critically impact the system; 🔵 Trivial — Low-impact suggestions for code quality improvements; ⚪ Info — Informational comments or context without requiring action" — plus six content-category badges (Security & Privacy, Stability & Availability, Data Integrity & Integration, Functional Correctness, Performance & Scalability, Maintainability & Code Quality) [verified: fetched, S1].
- Qodo: High / Medium / Low, where the threshold semantics are explicit: 3 = High only ("Blocking or critical issues"), 2 = High+Medium ("Important but non-blocking issues, plus critical ones"), 1 = all [verified: fetched, S15].
- GitHub Copilot: "Copilot labels each comment with a severity level of 'High,' 'Medium,' or 'Low' to help you prioritize the issues it finds based on their importance" [verified: fetched, S18].
- Greptile: `strictness` 1 (verbose) / 2 (default) / 3 (critical only) plus a `commentTypes` axis (logic/syntax/style) — two orthogonal dials: how important an issue must be, and what categories count at all [verified: fetched, S8].
- Sourcery: per-comment type labels (`issue (bug_risk):` vs `nitpick (performance):`) with security visually escalated (🚨) and a blocking/not-blocking status-check outcome [verified: fetched, S19].
- Practitioner (Jet Xu): a three-tier harm model — "Tier 1: Would cause production failures (crashes, breaking changes, security holes); Tier 2: Would cause maintainability issues (architectural violations, performance regressions); Tier 3: Subjective noise (style suggestions…)" with "Signal Ratio = (Tier 1 + Tier 2) / Total. If <60%, your tool is a noise generator" [verified: fetched, S21].

**Calibration is structural, not prompt-based — the strongest verified lesson.** CodeRabbit's noise guide is explicit about ordering: "If reviews feel noisy, change the settings that control volume first, then add instructions… from the biggest effect to the smallest. Apply them one at a time, so you can see which one helped" [verified: fetched, S3]. The volume control is the profile: quiet = "Only critical and major comments with a high effort-to-reward ratio. The rest go into collapsed sections of the review summary"; chill (default) = "Critical, major and minor comments, up to 20, then it collapses minor comments and then major ones"; assertive = "Every severity" [verified: fetched, S3]. And the division of labor: "An instruction only guides the model. The profile is the structural volume control, so use both" [verified: fetched, S3]. Qodo mirrors this: severity thresholds "applies only to inline comments. A finding below the threshold still appears in the summary, it's never dropped entirely" [verified: fetched, S15]. Greptile's escalation ladder when even strictness 3 is noisy: "Reduce comment types to ["logic"] only → Add more ignore patterns → Consider autoReview: [] → Give the learning system 2-3 weeks to adapt to your reactions" [verified: fetched, S8].

**Why prompting alone fails (Greptile's measured experience).** Greptile's initial output was "~19% were good, 2% were flat-out incorrect, and 79% were nits" [verified: fetched, S6]. "even with all kinds of prompting tricks, we simply could not get the LLM to produce fewer nits without also producing fewer critical comments"; few-shot good/bad examples "made the bot even worse because it… inferred superficial characteristics"; and an LLM-as-a-judge severity filter (rate own comments 1–10, drop <7) failed because "The LLMs judgment of its own output was nearly random" [verified: fetched, S6]. Their working fix was external (per-team embedding clustering of past accepted/downvoted comments — see Q3) [S6]. Jet Xu's independent practitioner framing agrees: "Filter by Impact: Only flag issues that cause observable harm… Resist Overreporting: Trust that fewer, actionable comments are better" [verified: fetched, S21].

**Severity labels are where noise concentrates (measured).** MegaLens's self-audit found severity "did worse" than correctness: of 9 sampled findings labelled critical, "0/9 (0% to 30%) were rated critical by both checkers", and "The labels look like they were set by pattern: a secret, a missing check, a missing signature. They do not reflect whether the code is ever called, or what an attacker could actually do with it. Code that nothing in the app calls was labelled critical twice" [verified: fetched, S22]. [inferred] Practical rule: a Critical label requires a demonstrated consequence (reachable code + observable harm), not a pattern match; this is exactly CodeRabbit's quiet-profile criterion of "high effort-to-reward ratio" [S3] and Jet Xu's Tier-1 definition [S21].

**Nitpick flooding is the default failure.** "In a PR with 20 changes, it would leave as many as 10 comments, at which point the PR author would simply start ignoring all of them" [verified: fetched, S6]; "Most AI code review tools generate 10-20 comments per PR. The problem? 80% are noise" [verified: fetched, S21]. The verified countermeasures, in order of strength: (1) structural volume control (profile/threshold/cap + collapse) [S3][S15]; (2) category filtering (drop `style`/`syntax`, keep `logic`) [S8]; (3) scope instructions ("Comment only on issues that block merging: bugs, security, data loss. Ignore style and formatting. Linters cover them. Mention a repeated pattern once, at summary level." [S3]); (4) learned suppression from team feedback (Q3) [S6][S10][S5]. [R3 cross-ref] Claude Code's `/code-review` guidance is the same lesson from the open-tool side: "report gaps that affect correctness and skip style… A reviewer that's asked to find problems will always find something. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen."

### Q3 — Anti-false-positive design: evidence requirements, confidence thresholds, suppression and feedback loops

**Evidence requirements (what a finding must carry):**
- **Exact location + what/why/how + suggested fix.** Qodo's finding anatomy is "severity, evidence, and recommended fix"; every finding explains "What needs attention / Why it matters / How to move forward" [verified: fetched, S14]. Sourcery posts "per-line feedback, posted as native review comments on the lines in question" with a type label and, where possible, "a suggestion block you apply with GitHub's Commit suggestion button" [verified: fetched, S19].
- **Rule citation.** "A comment that comes from one of your agent instruction files quotes the rule it breaks and links to it" [verified: fetched, S19]; Graphite's exclusions/rules are shown "with their metrics" so the team can see which rules fire and how often [verified: fetched, S30]. [inferred] A finding that cites a rule (or a tool rule ID) is checkable; a finding that asserts a preference is not.
- **Tool attribution.** CodeRabbit's 🧰 Tools section lists linter/scanner findings "with each tool's own severity and rule ID" — deterministic findings stay attributed to the deterministic tool [verified: fetched, S1].
- **Context-verification checks before accepting a finding** (MegaLens, all checkable): "Check how much of the project the review actually saw. A finding about code that was never shown to the reviewer is a guess"; "Before accepting 'X is missing', follow the call one level down and look at the database constraints"; "Ask whether the behaviour is what the app is supposed to do. If it is, it is not a vulnerability"; "before acting on a critical label, confirm the code is reachable and that the app is deployed the way the finding assumes" [verified: fetched, S22]. The academic mirror: ICML 2025 lists "capturing relevant context" as challenge #1 and solves it with "code slicing algorithms for context extraction" [verified: fetched, S24].
- **Reachability + intent as severity gates.** "Code that nothing in the app calls was labelled critical twice" [verified: fetched, S22]; "Intended behaviour read as a flaw" is a top false-positive cause [S22]. [inferred] The rule: a finding must state the concrete failure scenario (input/state → bad outcome) and confirm the code path is reachable; "it's supposed to work that way" must be checked against the spec/linked ticket before flagging (Qodo's requirement-gap agent does exactly this against linked specs [S14]).

**Confidence thresholds / filtering:**
- **LLM self-judgment is not a viable threshold.** "The LLMs judgment of its own output was nearly random" [verified: fetched, S6]. [inferred] So confidence gates must be external: deterministic filters (severity profile, category filter, path filters), learned filters (embedding similarity to past downvotes), or a second model from a different family (model inversion [S7]).
- **External clustering filter (Greptile's verified working mechanism).** Per-team embeddings of past comments in a vector DB; "If the comment had a cosine similarity exceeding some threshold with at least 3 unique downvoted comments, it would get blocked. The same situation but with three upvoted comments, it would pass. If neither or both, it would pass." Result: address rate 19% → 55%+ in two weeks; "most nits can be placed into a small number of clusters" [verified: fetched, S6].
- **Filtering as a first-class pipeline stage.** Qodo: "filtering out low-impact or irrelevant comments before they reach the pull request" [verified: fetched, S14]; ICML 2025: "a filtering mechanism for FAR reduction" [verified: fetched, S24]; CodeRabbit: profile-based collapse of below-threshold comments [verified: fetched, S3].
- **"Only flag what you can prove."** [inferred] No fetched vendor states this verbatim; the verified equivalent formulations are: Jet Xu's "Only flag issues that cause observable harm" [S21]; MegaLens's "a finding about code that was never shown to the reviewer is a guess" [S22]; Qodo's mandatory evidence field [S14]; CodeRabbit's tool-attributed findings [S1]; and [R3 cross-ref] the R3 evidence rule ("no bare claims"). [inferred] Synthesis for S10: a finding is allowed to exist only if it can cite (a) the exact file:line, (b) the code that makes the claim true, and (c) the concrete harm; otherwise it must be emitted as "could not verify" or dropped.

**Suppression / feedback loops (the verified mechanisms):**
- **Reactions + commit-based learning (Greptile).** Learning from "replies to Greptile" (positive / context-setting / dismissive), 👍/👎 reactions, and "Commit-Based Learning: Greptile analyzes which comments get addressed by comparing first and last commits"; adaptive noise filtering: "Missing semicolons (suppressed after 3 ignores)… Security issues (always flagged)… Logic errors (never suppressed)"; auto-generated rules from observed team comments [verified: fetched, S10]. Quality metric: "percentage of generated comments that the author actually addresses" [verified: fetched, S6].
- **Natural-language learnings with scope + relevance gating (CodeRabbit).** Learnings are "flexible, natural-language statements about code-review preferences" (file-pattern / repo / org scope); "CodeRabbit then evaluates the learning against the changed code and applies it only when it is relevant to that change"; best practices: "Consider if it's a pattern or a one-off", "Explain the why, not just the what"; "Require approval before applying learnings" [verified: fetched, S5].
- **Dismiss-with-reason (Qodo).** "Close a finding without fixing it and record why… showing that the finding was deliberately dismissed rather than simply missed" [verified: fetched, S16]; plus "Qodo continuously learns from how your team has handled similar findings in the past" and evolving Review Standards as the "single source of truth" [verified: fetched, S14].
- **Rule metrics + narrow exclusions (Graphite).** Rules and exclusions are shown "with their metrics"; exclusions must be scoped (broad "Don't suggest performance improvements" is called out as a bad example that "would miss legitimate performance issues") [verified: fetched, S30].
- **Copilot's per-comment feedback** ("We use this information to improve the product and the quality of Copilot's suggestions") [verified: fetched, S18].
- [inferred] Common design: feedback is recorded per finding (accept / dismiss+reason / downvote), aggregated per finding-type, and applied as (a) a suppression threshold (e.g., suppress after N ignores — Greptile's "3 ignores" [S10]), (b) a learned natural-language rule (CodeRabbit learnings [S5], Graphite auto-rules [S30]), or (c) a routing change (Qodo publishing locations [S15]). Safety rails: security and logic-error findings are never auto-suppressed [S10]; suppressions should be reviewable/exportable (CodeRabbit's KPI cards + export/import [S5]).

### Q4 — Diff-scoping heuristics for large diffs (chunking, hunk-level vs. file-level, context, generated code)

**Skip-lists are the first scoping decision (all vendors, verified):**
- CodeRabbit: "CodeRabbit already skips lock files, binaries, generated code and build output" by default; user `path_filters` are Minimatch globs where "Exclusions always win" and "A single include pattern turns the list into an allowlist" (explicit warning against accidental allowlists); plan file-limits "count only the files left after path filters, so if your pull requests often hit it, exclude files that don't need review, such as generated code, localization files or snapshots" [verified: fetched, S4].
- Greptile: `ignorePatterns` — "*.generated.* / **/*.test.js / **/node_modules/** / *.config.js / package-lock.json / *.md"; "Ignoring generated/vendor files can speed up reviews by 30-50% and eliminate irrelevant comments" (vendor-claimed speedup); bot authors (dependabot[bot], renovate[bot]) excluded from review entirely [verified: fetched, S8].
- Qodo: ignore PRs by title regex (default `["^\\[Auto\\]", "^Auto"]`), branch, author, label; ignore "generated files by language/framework"; "reduce noise from automated changes, generated code, or areas that are out of scope" [verified: fetched, S17].
- [inferred] A homelab skip-list: lockfiles, `*.generated.*`/`dist/`/`build/`, vendored deps, binaries/images, i18n/locale files, snapshots, docs (unless the diff is docs), and bot-authored PRs.

**Size-aware scoping and effort scaling:**
- Greptile's 24,300-PR study gives the baseline distribution: median PR = 3 files / 38 additions / 10 deletions (mean 10.3 files); and "the classic programmer meme is that small changes get many comments and large changes get very few. Turns out, this is at least somewhat grounded in reality" (the "lazy review" hypothesis — large PRs get less scrutiny, partly urgency, partly reviewer laziness); "enormous PRs that were merged super fast" are often "programmatic PRs, for example running prettier --write" [verified: fetched, S12]. [inferred] Scoping rules: (a) detect formatter/programmatic diffs first and review them as a class (or skip), (b) for PRs far above the ~3-file median, raise effort rather than depth-per-line, (c) expect and plan for the fact that human attention decays with size — the AI pass is the only review a large diff may get, so it should prioritize risk over completeness.
- Effort scales with size/risk: Copilot "Adaptive… based on the complexity and risk of your pull request" with cost "depending on factors such as pull request size" [verified: fetched, S18]; Greptile tiers "let Greptile pick per PR" [verified: fetched, S9]; CodeRabbit pauses incremental auto-reviews ("pauses after five reviewed commits") to bound repeated work [verified: fetched, S3].
- **Monorepo/per-directory scoping.** Greptile: "child directories can override the root setting — for example, a packages/db/.greptile/config.json with 'strictness': 1 makes database reviews stricter while the rest of the repo stays at 2" [verified: fetched, S8]; CodeRabbit has a dedicated monorepo guide (per-package instructions/filters/tools) [verified: fetched, S3 nav]. [inferred] Per-directory config is the verified pattern for heterogeneous repos (like a homelab).

**Chunking / unit of analysis:**
- [inferred, from verified pieces] No fetched source describes a numeric "max N lines per chunk" rule. The verified pattern is: (1) file-level LLM analysis with retrieved context (Greptile's per-changed-function graph queries [S11]; Qodo's per-file findings with repo context [S14]); (2) PR-level summary pass over the whole change (Sourcery's guide: "a table of what changed in each file and why" [S19]; CodeRabbit walkthrough [S1]); (3) incremental re-review scoped to newly added changes only ("Focus on newly added changes… Maintains conversation context" [S1]); (4) context extraction via "code slicing algorithms" rather than raw whole-file dumps [S24]; (5) cheap-model pre-filtering of which files are worth frontier-model attention ("a narrower, higher signal set of files can then be passed into the frontier model" [S7]).
- **Hunk-level vs. file-level.** Verified: findings are posted at line/hunk granularity ("per-line feedback… on the lines in question" [S19]; inline comments on covered lines [S1][S15]), while analysis context is file-plus-repo [S11][S14]. [inferred] For S10: analyze per file (with surrounding context), emit findings per hunk/line, summarize per PR.
- **Surrounding context is a false-positive control, not a nicety.** MegaLens's #1 false-positive cause is "Thin input": the reviewer reasoned "about a server that did not exist" because the slice lacked the relevant code — "A finding about code that was never shown to the reviewer is a guess" [verified: fetched, S22]. Greptile's graph exists precisely because "Most code review tools analyze files in isolation, missing critical relationships" [verified: fetched, S11]. Qodo's four context sources include linked tickets/requirements — intent context [S14]. [inferred] Minimum viable context for a finding: the changed hunk, the enclosing function/file, direct callers/callees, and the repo's stated rules/spec for that area.

### Q5 — Practitioner and study evidence: what users actually keep vs. dismiss

**Industrial study (ICSE 2025 SEIP — the most direct "kept vs. dismissed" data).** Qodo PR Agent in the wild: 238 practitioners, 10 projects, 4,335 PRs, 1,568 auto-reviewed; "73.8% of automated comments were resolved. However, the average pull request closure duration increased from five hours 52 minutes to eight hours 20 minutes"; "Most practitioners reported a minor improvement in code quality"; drawbacks: "faulty reviews, unnecessary corrections, and irrelevant comments" [verified: fetched, S23]. [inferred] Read: roughly 3 in 4 comments were at least touched (resolved = fixed or dismissed), but the net effect on cycle time was negative and perceived quality gain was minor — volume without triage costs more than it saves.

**Large-scale OSS study (278,790 conversations, 300 projects).** "code suggestions made by AI agents are adopted into the codebase at a significantly lower rate than suggestions proposed by human reviewers. Over half of unadopted suggestions from AI agents are either incorrect or addressed through alternative fixes by developers. When adopted, suggestions provided by AI agents produce significantly larger increases in code complexity and code size than suggestions provided by human reviewers"; humans add what AI lacks — "understanding, testing, and knowledge transfer" — and "exchange 11.8% more rounds when reviewing AI-generated code" [verified: fetched, S25]. [inferred] Two design consequences: (a) the majority of unadopted AI findings are wrong or redundant — precision, not recall, is the bottleneck; (b) AI suggestions tend to bloat code (larger complexity/size increases when adopted) — the reviewer prompt should prefer minimal fixes and flag "fix grows the code" as a smell.

**Measured noise baseline and its fix (Greptile).** Before noise control: 19% good / 2% incorrect / 79% nits, and at 10 comments per 20-change PR "the PR author would simply start ignoring all of them" [verified: fetched, S6]. After the clustering filter: address rate 19% → 55%+ [S6]. [inferred] Address-rate is the single most honest "kept vs. dismissed" metric a reviewer can track.

**Practitioner measurement (Jet Xu).** "Most AI code review tools generate 10-20 comments per PR. The problem? 80% are noise." In three real PRs, a 14-comment tool "missed every critical bug (21% signal)" while an 18-comment tool "caught a bug that would crash the entire job scheduler (61% signal)" — comment count and quality are uncorrelated [verified: fetched, S21].

**Self-audit (MegaLens).** 160 findings across 30 apps; on the 16 findings two independent checkers agreed on, 7 (44%, CI 23–67%) were false positives; 0/9 "critical" labels survived both checkers [verified: fetched, S22]. [inferred] Even a vendor's own security review, fact-checked by two other models, loses about half its findings and all of its criticals — the operator must treat any AI review (including S10's) as a triage aid, not a verdict.

**Benchmark evidence.** c-CRAB (built from human reviews, with generated held-out tests): "the existing review agents taken together can solve only around 40% of the c-CRAB tasks" (PR-agent, Devin, Claude Code, Codex), and "agent reviews often consider different aspects from the human reviews" [verified: fetched, S26]. LLM capability ceiling: with problem descriptions, GPT4o classified code correctness 68.5% and corrected 67.8% of the time; "Without problem descriptions, performance declined" — context/spec materially change accuracy [verified: fetched, S27]. Background: 119-paper SLR on automated code review [S28]; 100-developer survey: review stays essential, with "emerging tensions concerning understanding, accountability, and trust" [S29].

**Synthesis of what users keep vs. dismiss.** [inferred, from S23/S25/S6/S21/S22] Users keep findings that are (a) high-severity with a concrete, reachable failure scenario, (b) tied to a rule/standard the team recognizes, (c) small and actionable (one-line fix / suggestion block), and (d) novel (not something the team's linters or past reviews already said). Users dismiss findings that are style nits, pattern-matched severity without reachability, duplicates of linter output, about code the reviewer didn't actually read, or that push code bloat. The tools that improved "kept" rates did so with external, team-specific feedback loops (clustering [S6], learnings [S5], dismiss-reasons [S16], rule metrics [S30]) — not with better prompting alone [S6].

## Implications for the S10 code-reviewer build

Concrete design inputs for the S10 `code-reviewer` skill (static review in the kanban QA stage). Every item is grounded in a verified source (S#) or flagged [inferred]. This is the section the S10 build cites.

### 1. Review prompt shape

**Two-pass structure (verified pattern across CodeRabbit/Qodo/Sourcery [S1][S14][S19]):**
- **Pass 1 — PR/change summary (cheap, whole-diff).** Output: what changed, per-file "what and why" table, where the risk is, overall risk level. Mirrors Sourcery's summary-in-description + reviewer's guide [S19] and CodeRabbit's walkthrough [S1].
- **Pass 2 — Findings (per file, with context).** One analysis unit per changed file (hunk + enclosing function + retrieved context [S11][S14]); findings emitted at line granularity [S19].

**The findings-pass prompt must contain (all verified patterns):**
1. **Scope fence.** "Report only issues that block merging or cause observable harm: bugs, security, data loss, broken contracts. Skip style and formatting — linters own those. Mention a repeated pattern once, at summary level." (CodeRabbit's recommended instruction [S3]; [R3 cross-ref] "skip style" warning.)
2. **Specific bug classes to look for** — not a free "find problems": e.g., null/undefined handling, off-by-one/boundary, race/concurrency, resource leaks, error-swallowing, injection/authz, API-contract breaks (Greptile: "instruct it to look for specific types of bugs" [S7]; CodeRabbit's six category badges as a ready-made checklist [S1]).
3. **Explicit no-nitpick order** (Greptile's prompt improvement #1 [S7]).
4. **Fixed finding format** (Qodo's what/why/how [S14] + Sourcery's labels [S19] + CodeRabbit's severity [S1]):
   ```
   [SEVERITY: critical|major|minor|trivial] [CATEGORY: security|correctness|stability|data|performance|maintainability]
   file:line — <one-line title>
   What: <the problem, quoting the offending code>
   Why: <concrete failure scenario: input/state → bad outcome; reachability stated>
   Fix: <minimal suggested change (code block)>
   Evidence: <what was read to verify this (files/lines); rule cited if a repo rule is violated>
   ```
5. **Rule citation:** if a finding violates a repo rule (AGENTS.md / skills / standards file), quote the rule and its path (Sourcery [S19]; Graphite [S30]).
6. **Escape hatch:** "If you cannot verify a suspected issue from the code you were given, output it under `Could not verify` with what you'd need — do not emit it as a finding" [inferred; consistent with S22's "a finding about code that was never shown to the reviewer is a guess" and R3's "Unknown" rule].
7. **Fresh context.** Run the review in a fresh session/subagent that has not seen the author's reasoning [R3 cross-ref]. [inferred] If the author model is known and a second model family is available, prefer the different family (model inversion, +~10% catch rate [S7]) — optional at homelab scale.

### 2. Severity taxonomy

**Four levels (CodeRabbit's, minus Info [S1], aligned with Qodo/Copilot's High/Medium/Low [S15][S18]):**

| Level | Definition (verified wording, adapted) | Routing |
|-------|----------------------------------------|---------|
| **Critical** | "Severe issues that could cause system failures, security breaches, or data loss" [S1] — AND the failure path is reachable and the harm is concrete [S22] | Inline / blocking; always shown |
| **Major** | "Significant problems that impact functionality or performance" [S1] ("important but non-blocking" [S15]) | Inline / shown |
| **Minor** | "Issues that should be addressed but don't critically impact the system" [S1] (maintainability/perf [S21]) | Summary section only (collapsed) |
| **Trivial** | "Low-impact suggestions for code quality improvements" [S1] | Summary section only, capped; default-suppressed |

**Calibration rules (verified):**
- **Structural volume control, not prompt-only.** Cap inline findings (CodeRabbit's chill profile: "up to 20, then it collapses minor comments and then major ones" [S3]); below-threshold findings are routed to the summary, "never dropped entirely" (Qodo [S15]) — the operator must always be able to see what was suppressed.
- **Critical requires a proven consequence, not a pattern match.** "Code that nothing in the app calls was labelled critical twice" [S22]; require: reachable code + concrete input/state → harm + statement of what was checked (MegaLens's checks [S22]; "high effort-to-reward ratio" [S3]).
- **Category filter as a second dial** (Greptile's logic/syntax/style [S8]): S10 default = correctness + security + stability + data; performance/maintainability only as Minor; style = off (linters own it [S3]).
- **Effort scales with change size/risk** (Copilot Adaptive [S18]; Greptile per-PR tiers [S9]): small diff → full pass; large diff → risk-prioritized pass with explicit "reviewed X of Y files, skipped Z (reasons)" in the summary [inferred].
- **Target metric:** signal ratio ≥ 60% (Jet Xu: "If <60%, your tool is a noise generator" [S21]); track address rate (fraction of findings the operator actually acts on) as Greptile's metric [S6].

### 3. Evidence rules

1. **No bare claims.** Every finding cites exact `file:line`, quotes the offending code, and states the concrete failure scenario (S14's evidence field; S19's per-line posting; S22's checks) [verified: fetched].
2. **Read before you flag.** Before emitting "X is missing": follow the call one level down, check constraints/config, and confirm the behavior isn't intended (MegaLens's three causes [S22]). Minimum context for a finding: changed hunk + enclosing function + direct callers/callees + the repo rule/spec for that area [inferred; S11][S14][S24].
3. **Deterministic grounding first.** Run linters/typecheck/tests before the LLM pass; attach their output; the LLM must not re-emit linter findings (defer style to linters [S3]; tool findings keep tool + rule ID [S1]). [inferred] S10 order: (1) mechanical checks (lint/typecheck/tests), (2) LLM findings pass with the mechanical results in context, (3) findings that duplicate a mechanical result are dropped.
4. **No LLM self-judging of its own findings.** "The LLMs judgment of its own output was nearly random" [S6]. If a second-opinion filter is wanted, use a different model family [S7] or an external rule (suppression list, repo standards) — not the same model re-reading its own output.
5. **Rule-cited findings are checkable; preference findings are not.** Quote the rule for any standards-based finding [S19][S30].
6. **Record what was NOT covered.** The summary must list skipped files (with reasons) and any "Could not verify" items [inferred; S4's skip-list transparency + S22's thin-input lesson].
7. **Minimal-fix bias.** AI-adopted suggestions measurably increase code complexity/size more than human suggestions [S25] — suggested fixes should be minimal; a fix that adds abstraction for a one-line bug is a smell to flag in the finding itself [inferred].

### 4. Diff-scoping procedure

**Step 0 — Filter the diff (verified skip-lists [S4][S8][S17]):**
- Skip: lockfiles, binaries/images, generated code (`*.generated.*`, `dist/`, `build/`, `__pycache__`), vendored deps (`node_modules/`, `vendor/`), i18n/locale, snapshots, docs (unless the task is docs).
- Skip bot-authored changes (dependabot/renovate) [S8]; skip auto-titled PRs (`^[Auto]`, `^Auto` pattern [S17]).
- Use exclusion-only filters; never an accidental allowlist ("A single include pattern turns the list into an allowlist" [S4]).

**Step 1 — Size and classify the change (Greptile's distribution [S12]):**
- Baseline: median real PR ≈ 3 files / ~40 lines. Count files/lines; if far above baseline: (a) detect formatter/programmatic diffs (prettier-style mass changes) and review them as a class or skip with a note [S12]; (b) raise effort level rather than depth-per-line [S18][S9]; (c) prioritize by risk (security-sensitive paths, data paths, new public APIs) and state the prioritization in the summary [inferred].

**Step 2 — Per-file analysis with context (verified unit [S11][S14][S24]):**
- For each in-scope file: hunk + enclosing function + direct callers/callees + repo rules/spec for the area [inferred; S11][S14].
- Use cheap/fast analysis to pre-filter which files deserve deep attention ("a narrower, higher signal set of files can then be passed into the frontier model" [S7]) [inferred: at homelab scale, a single grep-based relevance pass is the analog].
- Context slicing, not whole-repo dumps [S24].

**Step 3 — Incremental on updates (verified [S1][S3]):**
- Re-review only newly added/changed hunks; maintain conversation context with prior findings; cap auto re-reviews (CodeRabbit pauses after 5 reviewed commits [S3]); don't re-emit unchanged findings (Greptile's naive-agent failure: "keeps finding new bugs every time you run it instead of reporting everything at once" [S7]).

**Step 4 — Route the output (verified [S3][S15]):**
- Inline (blocking view): Critical + Major, capped (≤20); Minor/Trivial → collapsed summary section; skip-list and "Could not verify" always visible in the summary.

**Step 5 — Feedback loop (verified [S5][S6][S10][S16][S30]):**
- Record every operator disposition per finding: fixed / dismissed+reason / downvoted (Qodo's dismiss-with-reason [S16]).
- Suppress a finding *type* after ~3 dismissals (Greptile's "suppressed after 3 ignores" [S10]) — implemented as an entry in a repo-local `review-learnings` file (natural-language, path-scoped, "explain the why, not just the what" [S5]).
- Never auto-suppress security or logic-error findings (Greptile's rails [S10]).
- Keep learnings reviewable/exportable (CodeRabbit's KPI cards + export [S5]); review them when they look stale ("Maintaining learnings over time" [S5]).
- Track address rate and signal ratio per review cycle; tune the profile one lever at a time and check the next few reviews ("Apply them one at a time, so you can see which one helped" [S3]).
