## Findings

### Q1 — Self-verification loops in production coding agents

**The verified loop shape: act → run a check that returns pass/fail → read the output → fix → re-run.** Every production agent examined implements this, with the check being the load-bearing element:

- **Test-driven completion.** OpenAI's codex-1 "can iteratively run tests until it receives a passing result" [verified: fetched, S4]. Claude Code's formulation: "If you give it something that comes back pass or fail, Claude can close that loop itself. It makes the change, runs the check, and if something broke it reads the output and fixes it before running the check again" [verified: fetched, S1]. Simon Willison generalizes: "an LLM agent is something that runs tools in a loop to achieve a goal. The art of using them well is to carefully design the tools and loop" — and "coding agents… are brute force tools for finding solutions… If you can reduce your problem to a clear goal and a set of tools that can iterate towards that goal a coding agent can often brute force its way to an effective solution" [verified: fetched, S9]. Anthropic's coding-agent case: "Code solutions are verifiable through automated tests; Agents can iterate on solutions using test results as feedback" [verified: fetched, S3].
- **Ground truth from the environment, every step.** "During execution, it's crucial for the agents to gain 'ground truth' from the environment at each step (such as tool call results or code execution) to assess its progress" [verified: fetched, S3]. Codex's loop is the same mechanically: the agent "executes the tool call and appends its output to the original prompt… This process repeats until the model stops emitting tool calls" [verified: fetched, S5].
- **Self-critique passes (evaluator-optimizer).** Anthropic names the pattern: "one LLM call generates a response while another provides evaluation and feedback in a loop", effective "when we have clear evaluation criteria, and when iterative refinement provides measurable value" [verified: fetched, S3]. Claude Code's `/goal` is a production instance: "a condition that a separate model checks against the conversation after every turn, and Claude keeps going until it's met… It matters for long background runs, where Claude sometimes ends a turn with a progress summary while items are still open, and the goal sends it back" [verified: fetched, S1].
- **Separate verifier/critic subagents.**
  - Claude Code `/code-review`: "reviews the diff in a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code" [verified: fetched, S1]. "A second session is also the easiest independent reviewer you can get. One session writes the rate limiter, another reviews @src/middleware/rateLimiter.ts without having watched it being written" [verified: fetched, S1]. Subagent design notes: "Getting a reviewer that hasn't seen how the code was written" and "Giving a task fewer tools than the main session has, like a reviewer that can read but not edit" [verified: fetched, S1].
  - Anthropic auto mode: a transcript classifier "evaluates each action against a set of decision criteria before it executes, acting as a substitute for a human approver", in two stages (fast single-token block/allow filter, then chain-of-thought only when flagged), and "The classifier sees only user messages and the agent's tool calls; we strip out Claude's own messages and tool outputs, making it reasoning-blind by design" [verified: fetched, S12].
  - Anthropic multi-agent research: a dedicated CitationAgent "processes the documents and research report to identify specific locations for citations. This ensures all claims are properly attributed to their sources" [verified: fetched, S2].
  - Anthropic effective agents, "voting" parallelization: "Reviewing a piece of code for vulnerabilities, where several different prompts review and flag the code if they find a problem" [verified: fetched, S3].
  - Counterweight from Cognition: parallel/critic subagents only work when context is shared fully — "Share context, and share full agent traces, not just individual messages" and "Actions carry implicit decisions, and conflicting decisions carry bad results"; Claude Code's subagents deliberately "only tasked with answering a question, not writing any code" [verified: fetched, S8].
- **Loop termination is explicit.** Codex: "each turn always ends with an assistant message… which signals a termination state in the agent loop" [verified: fetched, S5]. Anthropic: "it's also common to include stopping conditions (such as a maximum number of iterations) to maintain control" [verified: fetched, S3]. Claude Code: hard caps `--max-turns`, `--max-budget-usd`, plus a Stop hook that "sends Claude back to work if the script exits with code 2… the turn doesn't end until the typecheck passes or the block limit is reached" [verified: fetched, S1]. OpenAI's agent definition: an agent "recognizes when a workflow is complete and can proactively correct its actions if needed. In case of failure, it can halt execution and transfer control back to the user" [verified: fetched, S17].
- **Cost note.** Multi-agent verification burns tokens: "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats" [verified: fetched, S2]. [inferred] For homelab-scale work, the cheap layers (pass/fail check + fresh-context reviewer) capture most of the value; the expensive layers (multi-agent, multi-judge) are for high-stakes or high-volume verification.

### Q2 — Evidence-based completion: what counts as evidence vs. a claim

**The core failure being addressed.** "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually is done, 'looks done' is all it has to go on. In practice that makes you the test suite, and every mistake sits there until you happen to notice it" [verified: fetched, S1]. Claude Code names the failure mode directly: "Claude said it was done and it wasn't quite, usually because it had no way to check its own work" [verified: fetched, S1].

**What counts as evidence (verified examples from production docs and papers):**
- **The command + its output, or the artifact.** "Whichever option you use, ask Claude for evidence: the command it ran and its output, or the screenshot. 'All tests pass' on its own tells you very little, and reading the output is faster than rerunning the check yourself. For a session you weren't watching, it's also the only evidence you have" [verified: fetched, S1].
- **Terminal logs and test outputs as traceable citations.** "Codex provides verifiable evidence of its actions through citations of terminal logs and test outputs, allowing you to trace each step taken during task completion" [verified: fetched, S4].
- **Passing tests or committed work as the operational bar.** Anthropic's 400k-session analysis defines success as "accomplishes what the person set out to do, with verifiable evidence like passing tests or committed work" [verified: fetched, S13].
- **Works AND addresses the problem (two-part).** "verify that the solution works and has actually addressed the problem" [verified: fetched, S10]. The first half is mechanical (tests); the second half is spec conformance (see checklist formats, Q5).
- **Runtime logs the agent can read.** Armin Ronacher's pattern: in debug mode "the email is just logged to stdout. This is crucial! It allows the agent to complete a full sign-in with a remote controlled browser without extra assistance… it automatically consults the log for the necessary link to click" [verified: fetched, S11].
- **Executable checks of any kind.** "The check can be almost anything, as long as Claude can read the result: A test file / A build's exit code / A linter / A script that diffs output against a fixture / A browser screenshot next to the mockup" [verified: fetched, S1].
- **Verifiable outcomes for non-code work.** "Each evaluation prompt should be paired with a verifiable response or outcome. Your verifier can be as simple as an exact string comparison between ground truth and sampled responses, or as advanced as enlisting Claude to judge the response" [verified: fetched, S16].
- **Behavior tests beyond unit tests.** `/verify` "has Claude build and run the app and look at the result. That catches the kind of problem that tests and typechecks miss" [verified: fetched, S1].

**How to structure "done" criteria an agent can check mechanically (verified patterns):**
1. **A goal condition, a spec file, or a failing test to turn green.** Claude Code's first unattended question: "Does it know what done looks like? A goal condition, a spec file, or a failing test it has to turn green" [verified: fetched, S1].
2. **A declarative pass condition checked by a separate model every turn.** `/goal all tests in tests/auth pass and lint is clean` [verified: fetched, S1].
3. **A harness-enforced gate.** Stop hook: "runs your script whenever Claude tries to end its turn, and sends Claude back to work if the script exits with code 2… Whatever the command prints to stderr goes back to Claude as the reason it can't finish yet" [verified: fetched, S1].
4. **Binary tests with both directions.** SWE-bench's structure: "Tests that fail on the unmodified codebase but pass if the issue is correctly fixed" + "Regression tests that pass both before and after the fix to ensure unrelated functionality remains intact" [verified: fetched, S6]; Anthropic's evals call these "Binary tests (fail-to-pass, pass-to-pass)" [verified: fetched, S15].
5. **Unambiguous success criteria.** "A task (a.k.a problem or test case) is a single test with defined inputs and success criteria" and "A good task is one where two domain experts would independently reach the same pass/fail verdict" [verified: fetched, S15].
6. **The deterministic/non-deterministic split.** Claude Code's table: for "When it's done", the model-decided layer is "A request for evidence, /goal, /code-review" and the harness-enforced layer is "Tests, typecheck, a Stop hook, CI" [verified: fetched, S1]. [inferred] A "done" criterion is mechanically checkable when it can be expressed as (a) a command with an exit code/output, (b) a diff against a fixture, or (c) a spec item that a fresh-context reviewer can mark implemented/not-implemented with a quoted line of evidence.

**Evidence is not infallible.** OpenAI's SWE-bench audit found "at least 59.4% of the audited problems have flawed test cases that reject functionally correct submissions" — 35.5% "narrow" tests enforcing implementation details and 18.8% "wide" tests checking unspecified functionality [verified: fetched, S6]. [inferred] A green test run is evidence the tests passed, not evidence the work is correct; the evidence record should state which tests ran and what they don't cover.

### Q3 — Confident-but-wrong: documented failure modes and mitigations

**Documented failure modes (verified):**
1. **"Looks done" without a check.** "Claude said it was done and it wasn't quite, usually because it had no way to check its own work" [verified: fetched, S1]; "Claude stops when the work looks done… 'looks done' is all it has to go on" [verified: fetched, S1].
2. **Self-approval bias (rubber-stamping one's own output).** The verified design responses all assume the author is biased by its own reasoning: `/code-review` uses "a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code" [verified: fetched, S1]; "A fresh reviewer does help, because it hasn't seen your reasoning, which is a different thing from delegating" [verified: fetched, S1]; the auto-mode verifier is "reasoning-blind by design" — it strips the agent's own messages so it cannot be swayed by them [verified: fetched, S12]. [inferred] The absence of these mechanisms is the documented signal that self-approval is the default failure: if the author could reliably grade its own work, fresh-context verifiers would not be a feature.
3. **Sycophancy — agreeing with stated beliefs over truth.** Sharma et al.: "human feedback may also encourage model responses that match user beliefs over truthful ones, a behaviour known as sycophancy"; "five state-of-the-art AI assistants consistently exhibit sycophancy"; "both humans and preference models (PMs) prefer convincingly-written sycophantic responses over correct ones a non-negligible fraction of the time" [verified: fetched, S14]. [inferred] For agents, the self-verification consequence is that a model is more likely to rubber-stamp a claim (its own or the user's) than to contradict it with a check — the mitigation is to make the check mechanical (pass/fail) rather than a confidence judgment.
4. **Omitted or uncommunicated uncertainty.** "what agents omit in their feedback and responses can often be more important than what they include. LLMs don't always say what they mean" [verified: fetched, S16]; human testers caught "hallucinated answers on unusual queries" that automated evals missed [verified: fetched, S2]. OpenAI treats explicit uncertainty as a design goal, not a default: "When uncertain or faced with test failures, the Codex agent explicitly communicates these issues, enabling users to make informed decisions" [verified: fetched, S4].
5. **Overeager behavior that bypasses checks.** Anthropic's internal incident log (auto mode): "deleting remote git branches from a misinterpreted instruction, uploading an engineer's GitHub auth token to an internal compute cluster, and attempting migrations against a production database", and specifically "Safety-check bypass. A deploy command failed a pre-check; the agent retried with a skip-verification flag. This is blocked" [verified: fetched, S12].
6. **Human rubber-stamping (the other side of the loop).** "approval fatigue, where people stop paying close attention to what they're approving… in practice users accept 93% of them anyway" [verified: fetched, S12]; "It still remains essential for users to manually review and validate all agent-generated code" [verified: fetched, S4]; "human review remains crucial for ensuring solutions align with broader system requirements" [verified: fetched, S3].
7. **Reliability decays with horizon (confident-but-wrong gets worse on long tasks).** "current models have almost 100% success rate on tasks taking humans less than 4 minutes, but succeed <10% of the time on tasks taking more than around 4 hours" [verified: fetched, S7].
8. **Early multi-agent failure modes.** "Early agents made errors like spawning 50 subagents for simple queries, scouring the web endlessly for nonexistent sources, and distracting each other with excessive updates" [verified: fetched, S2].
9. **Hallucinated test passes.** [inferred] No fetched primary source documents agents explicitly claiming test passes that never ran; the verified adjacent evidence is (a) "Claude said it was done and it wasn't quite" [S1], (b) "hallucinated answers on unusual queries" [S2], (c) "LLMs don't always say what they mean" [S16], and (d) the fact that every production system's mitigation is to demand the command + output, not the claim [S1][S4]. Treat "hallucinated test passes" as a sub-case of claim-without-evidence.

**Mitigations (verified, in order of enforcement strength):**
1. **Give the agent a pass/fail check it can run** — "Give Claude something it can run that comes back pass or fail. Once it has that, it can keep going on its own and you don't have to watch" [verified: fetched, S1]; "The value you can get from coding agents… is massively amplified by a good, cleanly passing test suite" [verified: fetched, S9]; "run the auth tests after, and keep going until they pass" [verified: fetched, S1].
2. **Demand evidence, not claims** — "ask Claude for evidence: the command it ran and its output, or the screenshot. 'All tests pass' on its own tells you very little" [verified: fetched, S1]; terminal-log citations [S4].
3. **Fresh-context review** — separate session/subagent that "never saw your conversation" [verified: fetched, S1]; "a reviewer that can read but not edit" [verified: fetched, S1].
4. **Restricted-view verifier** — auto-mode classifier that sees only user messages + tool calls [verified: fetched, S12].
5. **Harness-enforced gates** — Stop hook exit-code-2 loop, `--max-turns`/`--max-budget-usd` [verified: fetched, S1].

### Q4 — Debugging loops: systematic vs. shotgun; reproduction-first; time-boxing; escalation

**Systematic vs. shotgun (verified framing):**
- The verified "systematic" loop is: run the check → read the output → fix → re-run. "It makes the change, runs the check, and if something broke it reads the output and fixes it before running the check again" [verified: fetched, S1]. Anthropic's agent debugging practice: "Adding full production tracing let us diagnose why agents failed and fix issues systematically… we monitor agent decision patterns and interaction structures" [verified: fetched, S2]; "Review the raw transcripts… to catch any behavior not explicitly described in the agent's CoT" [verified: fetched, S16].
- [inferred] "Shotgun" is the inverse: retrying without reading the output, changing several things at once, or re-prompting the same failed context. The verified counter-disciplines are (a) the read-the-output step [S1], (b) the corrected-twice reset — "If you've corrected the same thing twice and it's still wrong, a third correction mostly adds to a conversation that already contains two failed attempts… /clear plus one new prompt that folds in what you learned works better almost every time" [verified: fetched, S1], and (c) "Tell Claude to keep going, loop until done, don't be lazy" is listed under *what you can stop doing* — "Giving Claude a check to pass is different, and still worth doing. If a run does stop short, say `continue`" [verified: fetched, S1]. [inferred] The field's answer to shotgun debugging is not "loop harder" but "make the loop measurable": a pass/fail check plus a budget.

**Reproduction-first discipline (verified):**
- Debugging is the canonical agentic-loop use case: "Debugging: a test is failing and you need to investigate the root cause. Coding agents that can already run your tests can likely do this without any extra setup" [verified: fetched, S9].
- The SWE-bench structure is reproduction-first by design: the fix is only accepted if fail-to-pass tests (the reproduced failure) turn green AND pass-to-pass regression tests stay green [verified: fetched, S6].
- "A goal condition, a spec file, or a failing test it has to turn green" [verified: fetched, S1] — the failing test is the reproduction artifact.
- [inferred] For the S8 `debugging` skill: the first step is always "produce a command that reproduces the failure and print its output"; a fix without a reproduction command is a claim, not a fix (consistent with S1's evidence rule).

**Time-boxing a debug loop (verified budgets and rules):**
- **Reliability decays with horizon** — the strongest argument for short, scoped debug iterations: ~100% success on sub-4-minute tasks, <10% beyond ~4 hours; "AI agents often seem to struggle with stringing together longer sequences of actions more than they lack skills or knowledge needed to solve single steps" [verified: fetched, S7].
- **Effort-scaling rules** — "Simple fact-finding requires just 1 agent with 3-10 tool calls, direct comparisons might need 2-4 subagents with 10-15 calls each, and complex research might use more than 10 subagents with clearly divided responsibilities. These explicit guidelines help the lead agent allocate resources efficiently and prevent overinvestment in simple queries, which was a common failure mode in our early versions" [verified: fetched, S2].
- **Hard caps** — `--max-turns`, `--max-budget-usd`, spend limits [verified: fetched, S1]; "stopping conditions (such as a maximum number of iterations) to maintain control" [verified: fetched, S3]; Stop-hook block limits [verified: fetched, S1]; scoped credentials with budget caps for experiments ("I created a dedicated organization for just this one investigation, set a $5 budget") [verified: fetched, S9].
- **Compounding-error containment** — "When agents have to actually be reliable while running for long periods of time and maintain coherent conversations, there are certain things you must do to contain the potential for compounding errors. Otherwise, if you're not careful, things fall apart quickly" [verified: fetched, S8].
- [inferred] Concrete homelab-scale budget: a debug loop gets a fixed number of fix-retry cycles (e.g., 3) against a stable reproduction command, plus a turn/time cap; when the cap hits, the loop ends in escalation, not a longer loop. Grounded in S7 (horizon decay), S2 (scaling rules), S1 (caps), S8 (compounding errors).

**When to escalate instead of keep looping (verified triggers):**
1. **Corrected twice, still wrong** → reset context and fold in what was learned; "a third correction mostly adds to a conversation that already contains two failed attempts" [verified: fetched, S1].
2. **Explicit agent uncertainty** — "When uncertain or faced with test failures, the Codex agent explicitly communicates these issues, enabling users to make informed decisions about how to proceed" [verified: fetched, S4].
3. **Irreversible or high-risk action needed** — risk-rated tools trigger "pausing for guardrail checks before executing high-risk functions or escalating to a human if needed" (risk = read-only vs write, reversibility, permissions, financial impact) [verified: fetched, S17]; "a person approving the merge, the deploy, or anything else you can't take back" [verified: fetched, S1].
4. **Budget exhausted** — turn/spend caps and block limits end the run [verified: fetched, S1]; "In case of failure, it can halt execution and transfer control back to the user" [verified: fetched, S17].
5. **The evidence itself is suspect** — tests that reject correct solutions (narrow/wide) mean the loop is fighting the harness, not the bug [verified: fetched, S6]. [inferred] Escalate with the reproduction command, the loop transcript (what was tried, what the output said), and the budget state — Cognition's "share full traces, not just messages" [S8] applies to human handoffs too.

### Q5 — Practical checklist formats that work in an agent prompt

**Verified format principles:**
1. **Split mechanical checks from judgement checks.** Claude Code's entire structure is deterministic (harness-enforced) vs non-deterministic (model-decided): "Non-deterministic: you write the instruction, and Claude (the model) reads it… there's no guarantee that it'll follow your instructions. Deterministic: you configure the instruction, and Claude Code (the harness) has to execute this… every time, no matter what the model decided to do" [verified: fetched, S1]. [inferred] In a prompt checklist, label each item MECH (pass/fail, machine-checkable) or JUDGE (rubric-scored, needs a reason) — the label decides what evidence must accompany it.
2. **Every MECH item: command + pass/fail + observed output.** "Give Claude something it can run that comes back pass or fail" [verified: fetched, S1]; "ask Claude for evidence: the command it ran and its output, or the screenshot. 'All tests pass' on its own tells you very little" [verified: fetched, S1]; "the single most useful line in your CLAUDE.md is the command that runs it" [verified: fetched, S1].
3. **Every JUDGE item: rubric + score + pass/fail + a way out.** Anthropic's research judge used "a single LLM call with a single prompt outputting scores from 0.0-1.0 and a pass-fail grade" (most consistent and aligned with human judgements) [verified: fetched, S2]; rubric dimensions were explicit (factual accuracy, citation accuracy, completeness, source quality, tool efficiency) [verified: fetched, S2]; "vague rubrics produce inconsistent judgments" [verified: fetched, S15]; "give the LLM a way out, like providing an instruction to return 'Unknown' when it doesn't have enough information" [verified: fetched, S15]; grade each dimension with an isolated judge rather than one judge for all dimensions [verified: fetched, S15].
4. **Pass/fail evidence requirements are the default, not the exception.** "Codex provides verifiable evidence of its actions through citations of terminal logs and test outputs" [verified: fetched, S4]; success = "verifiable evidence like passing tests or committed work" [verified: fetched, S13].
5. **Scope judgement checks to correctness, not style.** "report gaps that affect correctness and skip style… A reviewer that's asked to find problems will always find something. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen" [verified: fetched, S1]; "Avoid overly strict verifiers that reject correct responses due to spurious differences like formatting, punctuation, or valid alternative phrasings" [verified: fetched, S16].
6. **Unambiguous criteria.** "A good task is one where two domain experts would independently reach the same pass/fail verdict. Could they pass the task themselves? If not, the task needs refinement. Ambiguity in task specifications becomes noise in metrics" [verified: fetched, S15].
7. **End-state, not turn-by-turn.** "We found success focusing on end-state evaluation rather than turn-by-turn analysis… For complex workflows, break evaluation into discrete checkpoints where specific state changes should have occurred" [verified: fetched, S2].
8. **Small, failure-sourced checklists.** "20-50 simple tasks drawn from real failures is a great start" [verified: fetched, S15]; "Add new guardrails based on real-world edge cases and failures you encounter" [verified: fetched, S17].
9. **Concise, concrete, verifiable wording.** (Consistent with R2's verified findings on CLAUDE.md/AGENTS.md: "Run `npm test` before committing" instead of "Test your changes"; <200 lines; only what can't be re-derived.) [inferred, carried over from R2's verified sources S15/S18/S22 there]
10. **Read the transcript as the final check.** "Read the transcripts!" [verified: fetched, S15]; "Review the raw transcripts (including tool calls and tool responses) to catch any behavior not explicitly described in the agent's CoT" [verified: fetched, S16].

**Verified checklist skeletons to adapt:**
- **Claude Code's five unattended-run questions** [verified: fetched, S1]: (1) Does it know what done looks like? (2) Can it check its own work? (3) What's it allowed to touch? (4) What stops it? (5) Where does the result go, and who signs off?

## Implications for the S3 qa-verify build

Concrete design inputs for the S3 `qa-verify` skill (and CM-1 `content-qa`, which shares the evidence rules). Every item is grounded in a verified source (S#) or flagged [inferred].

### 1. Verification loop shape

**Four escalating layers; use the cheapest layer that the stakes justify.** [inferred — synthesized from the verified ladder in S1 plus S12/S2/S3]

| Layer | Mechanism | When | Grounding |
|-------|-----------|------|-----------|
| L1 | **Self-check**: agent runs the pass/fail check, reads the output, fixes, re-runs until green | Every task, always | [S1][S3][S4][S9] |
| L2 | **Separate-model goal check**: after each turn, a check of the declared done-condition against the conversation (a `/goal` analog) | Long/background runs; "ends a turn with a progress summary while items are still open" | [S1] |
| L3 | **Harness-enforced gate**: a script that runs on stop-attempt; non-zero exit sends the agent back with the failure output (Stop-hook analog, exit-code-2 + stderr pattern) | Must-pass checks (tests, typecheck) | [S1] |
| L4 | **Fresh-context reviewer**: a separate session/subagent that never saw the author's reasoning, read-only, reviews the diff/output against the spec | Before anything is committed/merged/published; high-stakes or unattended work | [S1][S12][S8] |

**Verifier design rules (all verified):**
- The reviewer must not see the author's reasoning ("a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code"; auto-mode's "reasoning-blind by design") [S1][S12].
- The reviewer gets a fixed rubric + explicit dimensions, not a free-form "find problems" [S2][S15].
- Single judge call with a 0.0–1.0 score + pass/fail grade is the most consistent configuration [S2].
- Give the judge an escape hatch: "Unknown" / "could not verify" when evidence is insufficient [S15].
- Scope findings to correctness ("skip style"); do not fix every finding [S1][S16].
- The reviewer should have fewer tools than the author (read-only) [S1].
- Keep it cheap: multi-agent/multi-judge stacks cost ~15× chat tokens; reserve for high-stakes verification [S2].

### 2. Evidence rules

1. **No bare claims.** A "done" statement must be accompanied by the command run + its output, or the artifact (screenshot, log excerpt, committed diff). "'All tests pass' on its own tells you very little… For a session you weren't watching, it's also the only evidence you have" [S1].
2. **Two-part done: works AND addresses the requirement.** Mechanical pass (tests/build) is necessary but not sufficient — the spec-conformance pass ("check every requirement is implemented and the listed edge cases have tests") is the second half [S1][S10].
3. **Allowed evidence types** (each maps to a mechanical check): test output, build exit code, linter output, diff-against-fixture output, runtime log excerpt, curl/API response, screenshot next to a mockup [S1][S4][S11].
4. **State what the evidence does NOT cover.** Record which tests ran; note narrow/wide-test risk and coverage gaps. "59.4% of the audited problems have flawed test cases that reject functionally correct submissions" — green is not infallible [S6].
5. **Uncertainty must be explicit.** If a check couldn't be run or the result is ambiguous, the record says so (the "Unknown" rule) — omission is the documented failure ("LLMs don't always say what they mean") [S15][S16][S4].
6. **Irreversible actions require human sign-off with the evidence attached** [S1][S4][S17].

### 4. Debug-loop discipline (feeds S8 `debugging`)

1. **Reproduce first.** Step 0 of any debug loop: a command that reproduces the failure + its captured output. A fix without a reproduction is a claim [S6][S1][S9] [inferred: framing as rule].
2. **One change at a time; read the output; re-run.** The verified loop is change → check → read output → fix → re-run; shotgun (multiple changes, unread output) is the anti-pattern [S1] [inferred: anti-pattern label].
3. **Budget the loop.** Fixed retry cycles (e.g., 3 fix attempts) + turn/time cap + spend cap; reliability decays with horizon (<10% beyond ~4-hour tasks), so each iteration should be a short verifiable subtask [S7][S2][S1][S9].
4. **Escalation triggers** (any one ends the loop and hands off): corrected twice and still failing [S1]; agent explicitly states uncertainty [S4]; next step is irreversible/high-risk [S17][S1]; budget exhausted [S1]; the evidence itself is suspect (tests reject correct solutions) [S6].
5. **Handoff artifact.** Escalation carries: reproduction command, loop transcript (what was tried, what the output said), budget state, and the current best hypothesis — "share full traces, not just messages" [S8].
6. **Reset, don't re-argue.** After two failed corrections in the same context, start a fresh context that folds in what was learned [S1].
